# Knotra v1: пакет, проверка и диагностика

Статус: нормативный проект контракта от 30 сентября 2026 года. [Структурная схема](../../schemas/knotra-v1.schema.json), [язык](v1.md), [исполнение](execution.md) и [профиль движка](engine-profile.md) дополняют этот документ. Полный валидатор и движок пока не реализованы.

## 1. Пакет исходников

Пакет имеет корневую директорию и один явно выбранный входной YAML Pipeline. Имя входного файла не фиксировано. Он включается автоматически; остальные файлы допускаются только по `spec.files`.

При загрузке вычисляется транзитивное замыкание: входной Pipeline разрешает свои files, файлы `pipeline.file` должны быть в разрешённом списке; после их чтения к манифесту добавляются их files. Каждый импорт обязан иметь kind Pipeline. Все пути, в том числе внутри импортированного документа, разрешаются относительно единого корня пакета. Файл промпта, схемы, кода или импорта должен находиться в этом манифесте. Повторное включение одного пути несколькими документами допустимо, две разные записи одного пути в архиве запрещены.

Загрузчик принимает только обычные файлы. Символические ссылки, hard links, устройства, сокеты, FIFO, абсолютные пути, выход за корень и конфликт файла с родительской директорией отклоняются. Имена должны быть уникальны также после Unicode NFC и ASCII case folding, чтобы один пакет не менял смысл между файловыми системами. Содержимое путей не нормализуется молча: ненормализованное имя вызывает ошибку. Проверка фактического корня обязательна даже после JSON Schema; одних регулярных выражений недостаточно.

Файлы, отсутствующие в манифесте, не передаются и не монтируются. Неявного включения всей рабочей директории, `.env`, домашней директории и содержимого Git нет. Переменные окружения внутри путей не подставляются. Архив не является способом обойти правила paths; упаковка — транспорт над тем же манифестом.

Манифест имеет точную форму `{entrypoint: Path, files: [{path: Path, size: integer, sha256: string}, ...]}` без дополнительных полей. `entrypoint` входит в files; записи files отсортированы по байтам UTF-8 пути. `size` — длина файла в байтах, `sha256` — 64 строчных шестнадцатеричных символа хеша содержимого. Идентификатор снимка равен `sha256:` и SHA-256 от UTF-8 сериализации манифеста по JCS (RFC 8785). Размеры в пределах точных целых IEEE-754. Комментарии, пробелы и переносы исходного файла входят в его хеш: изменение исходника или выбор другого entrypoint создаёт новый снимок.

План отдельно фиксирует нормализованные документы, версии языка/компилятора/адаптеров, эффективные настройки, разрешённые model IDs, digest образов, описания MCP-инструментов и их схем, ссылки на секреты. Значений секретов в снимке нет. План не делает ответы внешних моделей детерминированными и не заменяет историю выполненных действий.

## 2. Профиль YAML и JSON

- Один непустой документ UTF-8, YAML 1.2.2 Core Schema с дополнительными ограничениями ниже. YAML 1.1 не поддерживается; `yes`, `no`, `on`, `off` остаются строками.
- Только JSON-совместимое дерево значений. Все ключи объектов — строки; duplicate keys запрещены на любой глубине, до преобразования в обычную map.
- YAML anchors, aliases, merge keys `<<`, пользовательские и явные теги запрещены. Единственная допустимая директива — `%YAML 1.2`. Несколько документов, даже если последующие пусты, запрещены.
- Даты без кавычек не преобразуются в timestamp: Core Schema трактует их как строки. Если библиотека делает иначе, загрузчик должен настроить её либо отклонить документ.
- Для чисел допустима только JSON-лексика: `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?`. YAML hex/octal, `.inf`, `.nan`, ведущий `+` и числа с `_` запрещены как числовые литералы. Для такого текста следует использовать кавычки.
- Целочисленный токен без дробной/экспоненциальной части должен попадать в signed int64. Дробный/экспоненциальный токен преобразуется в конечный float64, с округлением IEEE-754; переполнение и ненулевое значение, ставшее нулём при underflow, отклоняются. JSON Schema `integer` принимает математически целое значение согласно стандарту независимо от написания.
- CEL получает целочисленные токены как `int`, дробные/экспоненциальные как `double`; правила преобразования не зависят от YAML-библиотеки. При последующей сериализации runtime сохраняет этот выбор типов в своём значении; формат хранения должен различать `1` и `1.0`, хотя оба удовлетворяют JSON Schema integer.
- Строки сохраняются после стандартного YAML-декодирования; текстуальные шаблоны не вычисляются. Непарные UTF-16 суррогаты и невалидный UTF-8 запрещены.

Пользовательские JSON-данные API и результаты кубиков следуют тем же числовым ограничениям, проверке duplicate keys и Unicode. Схемы из файла могут быть JSON или YAML, определяемыми расширением `.json`, `.yaml`, `.yml`; остальные расширения схем отклоняются. JSON-файл содержит ровно одно значение DataSchema.

## 4. Профиль CEL

Выражения используют семантику CEL: неизменяемые значения, отсутствие ввода-вывода, отсутствие eval пользовательского кода. Поддерживаются JSON-представимые `null`, `bool`, `int`, `double`, `string`, списки и карты со строковыми ключами. Артефактные handles не являются CEL-картами. Значение артефакта передаётся через Binding.from, включая iteration.item, а не через выражение.

Разрешены:

- Литералы перечисленных типов, доступ к полям/индексам данных, `in`, `size`.
- Арифметические, сравнительные, логические операторы CEL и тернарный оператор.
- Стандартные преобразования `int`, `double`, `string`, `bool` в тех перегрузках, которые принимает CEL; `type`.
- Строковые `contains`, `startsWith`, `endsWith`, `matches`.
- Стандартные macros `has`, `all`, `exists`, `exists_one`, `map`, `filter`.

`uint`, `bytes`, timestamp/duration-значения CEL, optional-types, proto-объекты, расширения строк/lists/sets/math, пользовательские функции, случайность, текущее время, сеть, файлы и env недоступны. Duration полей Knotra — отдельный лексический тип, не CEL-выражение. Регулярные выражения в `matches` следуют RE2. Числа проверяются на переполнение/нефинитность, карты с нестроковыми ключами не допускаются на выходе. Boolean-условие обязано вернуть bool; truthiness и преобразование строки в условие отсутствуют.

Полный набор перегрузок фиксируется сохранённым checked AST и версией реализации CEL в плане. Нельзя включать библиотечные расширения только потому, что они присутствуют в установленном пакете. Значения с пользовательской JSON Schema могут проверяться как dyn, если их точный CEL-тип не выводится; это не отменяет проверку реального значения на границе порта. Нельзя обещать полную статическую совместимость произвольных JSON Schema.

Статическая проверка знает области видимости из [основного контракта](v1.md). В namespace `nodes`, `inputs`, `args`, `state`, `body.outputs` первый идентификатор должен быть статически известен; доступ ко всему служебному namespace как значению, перебор nodes и вычисляемое имя порта запрещены. Динамическая индексация разрешена только ниже объявленного JSON-порта. Отсутствующий необязательный `args` можно проверять `has(args.x)`; отсутствие ссылочного графового источника обрабатывается до CEL по правилам missing и не скрывается через has.

Вычисления имеют лимит стоимости CEL, а не только wall clock. Для первой реализации используется стандартный runtime cost accounting cel-go, без пользовательских cost overrides, с лимитом 100000. Версия библиотеки фиксируется в движке и плане; изменение таблиц стоимости требует проверки совместимости перед обновлением. Превышение даёт `EXPRESSION_LIMIT`, не false и не missing. Контракт v1 не обещает идентичное число cost units при произвольной альтернативной реализации CEL: она должна воспроизвести выбранную модель стоимости или заявить несовместимость.

## 5. Проверка DataSchema

Каждая самостоятельная DataSchema сначала проверяется по разрешённому подмножеству, затем компилируется по Draft 2020-12. `$ref` разрешается относительно собственного корня: встроенная schema порта не может ссылаться на соседний порт, а schemaRef — не JSON Pointer. Все локальные цели должны существовать и быть схемами, циклы ссылок отклоняются. Значения default входных портов валидируются при подготовке.

Для `pattern` и ключей `patternProperties` допускается общий синтаксис RE2 и ECMA-262: литералы, `.`, классы и диапазоны, группы без специальных флагов, alternation, `* + ? {m,n}`, anchors `^ $`, экранирование метасимволов, `\d \D \s \S \w \W`, `\t \r \n`. Запрещены backreferences, lookaround, именованные группы, inline flags, Unicode properties и зависящие от режима расширения. Сопоставление неявно не якорится; `\d`/`\w` используют ASCII, `\s` — ASCII whitespace; `.` не включает LF, `$` совпадает только с концом строки (не перед завершающим LF). Это явное сужение профиля данных для одинаковой реализации в Go и других средах. Проверяющий движок обязан применять эти правила отдельно от библиотеки, если её regexp defaults отличаются.

Имена свойств, required и все остальные ограничения проверяются по семантике JSON Schema. Взаимно противоречивые ограничения, которые заведомо не принимают значения, сами по себе не делают схему синтаксически ошибочной: boolean false допустим. Однако несовместимый default отклоняется, а заведомо невозможная привязка между двумя портами диагностируется до исполнения, если несовместимость доказуема. Неопределённость совместимости не равна доказанной совместимости; реальные значения проверяются всегда.

## 6. Последовательность проверок

| Слой | Обязательные проверки | Когда |
| --- | --- | --- |
| `parse` | Размеры, кодировка, единственный документ, YAML-профиль, ключи и числа | При чтении каждого файла |
| `structural` | JSON Schema Knotra: поля, типы, discriminators, обязательность, формы Binding | До разрешения ресурсов |
| `package` | Манифест, допустимость путей, файлы промптов/схем/импортов, типы файлов, import cycle/depth | Локально, без внешних вызовов |
| `semantic` | Схемы данных, defaults, scope, ссылки, производные порты, DAG, CEL, правила конкретных типов, retry/defaults | После загрузки пакета |
| `admission` | Профиль, capabilities адаптеров, инструментов и sandbox, разрешения, лимиты, доступность образов/credentials, фиксация плана | На движке перед стартом |
| `input` | Значения входов, defaults, схемы JSON, зарегистрированные handles | Перед стартом Graph/кубика |
| `runtime` | Результаты, эффекты, бюджеты, timeout, отмена, артефакты | При исполнении |

Офлайн-проверка сообщает, какие проверки admission ещё не выполнены. Отсутствие движка или подключения не превращается в фиктивное подтверждение возможности исполнения. Операции discovery на admission допускают установление соединения и чтение каталога инструментов, но не вызов пользовательских инструментов ради проверки.

### Минимальный перечень семантических правил

1. Все локальные/канонические ресурсы и schemaRef существуют. Доступ проверяется для всех объявлений, включая неисполняемые ветки.
2. Все ссылки на порты существуют, включая производные выходы switch/foreach/loop/pipeline. Неверная область видимости отклоняется.
3. Зависимости `needs` и все статические чтения `nodes` образуют DAG внутри каждой области; self-reference и циклы запрещены. Экспорты графа не создают обратных зависимостей его узлов.
4. CEL разбирается и проверяется в точном контексте; условия возвращают boolean. Графовая зависимость не скрывается ленивой ветвью выражения.
5. JSON и артефакты не смешиваются. Artifact bindings — только from/coalesce; path на artifact запрещён. llm не принимает artifact. mount разрешён только у agent/code, обязателен для их артефактного входа; пути не пересекаются.
6. foreach.over указывает на массив/коллекцию; body exports обязательны, artifact exports одиночные. with соответствует body.inputs, обязательные входы покрыты binding/default.
7. loop.state.initial и next соответствуют портам состояния; body не экспортирует iterations/termination. Неизвестные имена state, некорректные initial/next scopes и next missing — ошибки, не обнуление состояния.
8. switch cases и default имеют уникальные имена; defaults не создают неявных ветвей.
9. Подпайплайны не образуют рекурсию; входы/выходы выводятся из child. permissions используют канонические имена; все запрошенные права и caps укладываются в предков.
10. У switch/human/foreach/loop/pipeline эффективное retry.maxAttempts равно 1. Тип кубика и external effects ограничивают повтор независимо от этого числового поля.
11. Env не переопределяет KNOTRA_*, argv не содержит NUL. collect — одиночный файл, MIME входит в разрешённые; коллекции собирает foreach.
12. URL, HTTP headers, host allowlists, secrets, capabilities, idempotencyArgument и provider parameters удовлетворяют [контракту профиля](engine-profile.md).

## 7. Диагностика

Каждая ошибка имеет стабильный `code`, `phase`, человекочитаемое `message`, логический путь `path` в формате JSON Pointer. Если ошибка относится к исходнику, обязательны `file` (путь в пакете), `line` и `column` (начинаются с 1). Для отсутствующего поля указывается содержащий объект; для EOF — позиция EOF. `related` — необязательный список дополнительных мест, например второй ключ или ребро цикла. Во время исполнения добавляются run/node instance/attempt/operation IDs, когда существуют. Текст и контекст ошибки не включают значения секретов.

Ниже базовые коды; адаптер может добавлять `details` с собственным машинным кодом, не заменяя основной смысл:

| Коды | Смысл |
| --- | --- |
| `YAML_INVALID`, `DUPLICATE_KEY`, `DOCUMENT_LIMIT` | Ошибка разбора или лимита документа |
| `SCHEMA_INVALID`, `VERSION_UNSUPPORTED`, `FEATURE_UNSUPPORTED` | Структура, версия или объявленная возможность не поддерживается |
| `PACKAGE_INVALID`, `IMPORT_CYCLE` | Файлы, пути, манифест или импорт |
| `REFERENCE_INVALID`, `SCOPE_INVALID`, `GRAPH_CYCLE` | Имя/область/зависимости |
| `DATA_SCHEMA_INVALID`, `DEFAULT_INVALID`, `TYPE_MISMATCH` | Схема данных, default или доказанное противоречие типов |
| `EXPRESSION_INVALID`, `EXPRESSION_FAILED`, `EXPRESSION_LIMIT` | Разбор/типизация, вычисление или стоимость CEL |
| `CONFIG_INVALID`, `PERMISSION_DENIED`, `CAPABILITY_UNSUPPORTED`, `SECRET_UNAVAILABLE` | Профиль, полномочия, возможности и credentials |
| `INPUT_INVALID`, `INPUT_UNAVAILABLE`, `OUTPUT_INVALID`, `OUTPUT_UNAVAILABLE` | Данные на границе Graph/кубика |
| `MODEL_FAILED`, `TOOL_FAILED`, `PROCESS_FAILED`, `ARTIFACT_INVALID` | Исполнитель/результат/файл |
| `TIMEOUT`, `CANCELLED`, `BUDGET_EXCEEDED`, `STEP_LIMIT`, `ITERATION_LIMIT` | Остановка исполнения |
| `OUTCOME_UNKNOWN` | Внешняя операция могла выполниться, но нет достоверного результата |

Missing обязательного входа кубика вследствие skipped-источника — штатный skip с причиной `dependency_missing`, а не `INPUT_UNAVAILABLE`; последний код относится к невозможности начать обязательный Graph/запуск или состояние цикла. Причины skip и коды ошибок различаются.

Валидатор может собрать несколько независимых ошибок. Он не выполняет dependent проверки на заведомо повреждённых объектах и не подменяет первопричину каскадом случайных ошибок. API формат ответа, transport status и CLI exit codes задаются последующим контрактом API/CLI.

## 8. Приёмочные сценарии исполнения

Таблица — обязательные ожидания для будущих тестов движка. Текущая проверка JSON Schema их не исполняет.

| Сценарий | Ожидаемое поведение |
| --- | --- |
| required input с default отсутствует / явно null | Вставка default в первом случае, проверка null по схеме во втором |
| when=false → потребитель обязательного выхода | Источник и затем потребитель skipped; никакого внешнего вызова |
| coalesce из двух веток, первая missing, вторая null | После завершения источников результат null |
| Поздняя ветвь coalesce упала, первая уже вернула данные | Запуск падает; coalesce не скрывает ошибку |
| Два foreach item завершились в обратном порядке | Массив результатов сохраняет исходный порядок |
| Пустой foreach | Пустые массивы/коллекции всех производных портов, тело не запускается |
| loop.until=true на первой итерации | iterations=1, termination=condition; next не вычисляется |
| until=false на maxIterations при return_last | Последнее тело опубликовано, termination=limit, next не вычисляется |
| Два loop.state.next читают разные старые значения | Оба видят старое state, затем замена атомарна |
| Подпайплайн попытался сбросить model/tool budgets | Операции учитываются также в родительских счётчиках |
| Код завершился с 0, файл отсутствует или JSON невалиден | OUTPUT_INVALID/ARTIFACT_INVALID; частичного успеха нет |
| Агент вызвал finish на последнем допустимом turn | Валидный результат принимается; другие tools уже не выполняются |
| Повтор write-инструмента без надёжной идемпотентности | После неизвестного исхода пауза/ошибка, не слепой повтор |
| Потеря worker после успешной публикации | Подтверждённый кубик не выполняется заново |
| Отмена одновременно с поздним результатом | Побеждает первая зафиксированная операция по правилам исполнения |
| Секрет модели указан в подключении | Доступен доверенному адаптеру, не env агента и не снимку плана |

## 9. Границы реализации и чистота кода

Будущая реализация должна сохранять простую последовательность: source loader с позициями → структурный валидатор → компилятор ссылок/CEL/графа → неизменяемый план → runtime. Нормализация defaults выполняется один раз и не смешивается с планированием. Общие порты, Binding, scopes и ошибки реализуются единообразно для всех типов кубиков.

Адаптеры модели, MCP, sandbox и storage не решают самостоятельно правила skip, retry, лимитов и публикации. Runtime работает с типизированным планом, а не читает произвольные YAML-поля на каждом шаге. Новые возможности не должны требовать неявного deep merge или скрытых глобальных переменных. Тесты проверяют наблюдаемое поведение и инварианты, а не воспроизводят внутренние функции ради покрытия.

В этом этапе поставляются контракт и контрольные документы. Проверка fixtures сверяет parse/structural expectations. Семантические ожидания и таблица runtime — будущие критерии приёмки; их нельзя считать пройденными до реализации соответствующих компонентов.
