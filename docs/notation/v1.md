# Knotra v1 notation contract

The implementation lives in `internal/contract`, `internal/engine` and `internal/adapters`. Setup is
described in the [running guide](../running.md); verified scenarios and support boundaries are in
the [report](../verification.md).

Status: normative v1 contract, checked against the implementation on 5 October 2026. The structural
JSON Schema and textual semantics apply together. External system requirements are checked at
admission; unsupported providers are rejected before execution.

The contract consists of four normative documents:

- This document: structure, types, bindings, scopes and every node type.
- [Execution](execution.md): scheduling, results, states, retries, files and recovery.
- [Engine profile](engine-profile.md): connections, sandboxes, secrets and permissions.
- [Validation](validation.md): packages, YAML, CEL, checks and diagnostics.

The [JSON Schema](../../schemas/knotra-v1.schema.json) defines the structural contract using Draft
2020-12. The text adds semantic constraints. A document is valid only when both parts are satisfied.
A disagreement between schema and text is a contract defect; implementations must not silently
choose a convenient interpretation. [Contract fixtures](../../contracts/v1/fixtures/README.md) check
the contract but do not replace it.

“Required”, “prohibited” and “must” express requirements. “By default” describes Knotra
normalization: a standard JSON Schema validator does not insert missing values itself.

## 1. Two document kinds

The root contains exactly four required fields:

| Field        | Type and value                      |
| ------------ | ----------------------------------- |
| `apiVersion` | String `knotra/v1`                  |
| `kind`       | `Pipeline` or `EngineProfile`       |
| `metadata`   | Metadata described below            |
| `spec`       | Specification for the selected kind |

`Pipeline` is a portable process description. `EngineProfile` is trusted configuration for a
particular engine. The engine operator selects the profile outside the pipeline package; a profile
file in a submitted package does not grant the process additional permissions.

`metadata.name` is required: 1–63 ASCII characters, beginning with a lowercase Latin letter,
followed by lowercase letters, digits or hyphens. Optional fields are nonempty strings `title`,
`description`, `version`, and `labels`, an object of string values. `metadata.version` identifies
the author's process version, not the language version; it does not determine package identity.

All control objects are closed: unknown fields are errors. Arbitrary keys are allowed only in
explicitly declared maps, user JSON values, schema data, labels and adapter parameters. Object key
order does not affect execution. List order matters.

## 2. Common types

| Type         | Rule                                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Identifier` | Full match of `[a-z][a-z0-9_]{0,63}`. Names of nodes, ports, state entries, resources and schemas                                                                         |
| `ToolName`   | 1–128 ASCII characters from `A–Z`, `a–z`, `0–9`, `_`, `-`, `.`; case-sensitive                                                                                            |
| `Duration`   | Positive integer without leading zeros followed by one unit: `ms`, `s`, `m`, `h`. Examples: `500ms`, `30m`; `0s` and `1h30m` are prohibited. Maximum 365 days             |
| `Path`       | Normalized relative POSIX path of 1–1024 characters. No empty segments, `.`/`..`, backslashes, control characters U+0000–001F/U+007F, leading `/` or Windows drive prefix |
| `Json`       | `null`, boolean, Unicode string, number, array or object with string keys. Only finite numbers; the numeric profile is defined in [validation](validation.md)             |
| `Argv`       | Nonempty string array. The first element is nonempty; subsequent elements may be empty. NUL is prohibited in every element. No interpolation or implicit shell            |
| `TextSource` | Exactly `{text: nonempty string}` or `{file: Path}`. The file is nonempty UTF-8 text from the package                                                                     |

Source files are read relative to the package root, not the current YAML file. `mount` and
`collect.path` are relative to the sandbox working directory; they use the same lexical `Path` type
with a different root.

## 3. Pipeline.spec

| Field       | Required | Meaning / behavior when absent                      |
| ----------- | -------- | --------------------------------------------------- |
| `files`     | No       | Unique list of included package paths; default `[]` |
| `schemas`   | No       | Map `Identifier → SchemaSource`; default `{}`       |
| `models`    | No       | Model map; default `{}`                             |
| `mcp`       | No       | MCP connection map; default `{}`                    |
| `sandboxes` | No       | Sandbox profile map; default `{}`                   |
| `secrets`   | No       | Secret reference map; default `{}`                  |
| `defaults`  | No       | Common execution and tool settings                  |
| `limits`    | No       | Stricter limits within the engine profile           |
| `inputs`    | No       | Map of `InputPort` input ports; default `{}`        |
| `nodes`     | Yes      | Nonempty map `Identifier → Node`                    |
| `outputs`   | Yes      | Nonempty map of `Export` exported ports             |

Identifiers are unique within their map. A model and an input may share a name because their
namespaces differ. References are case-sensitive. Nodes are not called in declaration order: the
engine constructs a dependency graph.

### Resources

| Map         | Entry fields                                                                                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `models`    | Required `connection`: connection name from `EngineProfile.spec.models`. Optional `model`: nonempty model override; `parameters`: adapter parameter object; `requires`: unique list of `toolCalling`, `structuredOutput`, `imageInput` |
| `mcp`       | Required `connection`: name from `EngineProfile.spec.mcp`. `session` defaults to `node`; alternative `run`                                                                                                                             |
| `sandboxes` | Required `profile`: name from `EngineProfile.spec.sandboxes`                                                                                                                                                                           |
| `secrets`   | Required `ref`: name from `EngineProfile.spec.secrets`                                                                                                                                                                                 |

Nodes use the local names of these resources. The exception is `pipeline.permissions`, which uses
engine profile names so renaming a local alias cannot bypass permissions.

`parameters` merge with connection parameters at the top level: a local value replaces the entire
value of that key. The registered adapter declares allowed keys and types; arbitrary transport
payloads cannot be passed here. Unknown parameters and unsupported capabilities are preparation
errors. v1 never silently selects another model or provider.

### Defaults and limits

`defaults` contains only optional `execution` and `tools`. Nodes in every nested Graph of the
current Pipeline inherit `execution` settings. A called Pipeline uses its own defaults; parent
constraints continue to apply.

`limits` contains positive `maxConcurrentNodes`, `maxNodeInstances`, `maxModelCalls`, `maxToolCalls`
and `timeout: Duration`. Each absent limit is inherited from the effective profile/parent.
Increasing an allowed limit is an error. `maxNodeInstances` includes every node instance, including
instances inside iterations; attempts do not create new instances. Counter and timing semantics are
defined in [execution](execution.md).

`defaults.tools` contains `mcp: {local_server: [ToolName, ...]}` and
`sandbox: [files.read, files.write, process.exec]`. Both maps/lists are empty by default. The tool
name list for each MCP server is nonempty and has no duplicates. Only `agent` nodes receive these
common permissions. They do not invoke tools automatically.

## 4. Data schemas and ports

JSON and file artifacts are separate value categories. An object resembling a file description does
not become an artifact. Every port specifies exactly one of:

- `schema: DataSchema`: inline JSON schema;
- `schemaRef: Identifier`: name in the current Pipeline's `spec.schemas`;
- `artifact: {mediaTypes: [...], collection?: false}`: file contract.

`SchemaSource` is a `DataSchema` or `{file: Path}` referring to a JSON/YAML schema in the package.
Every Graph inside a Pipeline uses that Pipeline's schema registry. A subpipeline has its own
registry.

### DataSchema

A closed profile of JSON Schema Draft 2020-12 is supported: boolean schemas `true`/`false` and
objects with the following keys:

- `$schema`, `$ref`, `$defs`, `$comment`, `title`, `description`;
- `type`, `const`, `enum`, `default`, `examples`;
- `properties`, `patternProperties`, `additionalProperties`, `propertyNames`, `required`,
  `minProperties`, `maxProperties`, `dependentRequired`, `dependentSchemas`;
- `items`, `prefixItems`, `contains`, `minContains`, `maxContains`, `minItems`, `maxItems`,
  `uniqueItems`;
- `minLength`, `maxLength`, `pattern`;
- `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`;
- `allOf`, `anyOf`, `oneOf`, `not`, `if`, `then`, `else`.

Key types and meanings follow the standard. If supplied, `$schema` equals
`https://json-schema.org/draft/2020-12/schema`. `$ref` is allowed only as a local JSON Pointer (`#`
or `#/...`) within a standalone DataSchema root. External references, `$id`, anchors, dynamic
references, `format` and unknown extensions are prohibited. Cyclic `$ref` chains are prohibited in
v1. Regular expressions are limited to the portable RE2/ECMA-262 subset defined in
[validation](validation.md).

Omitting `additionalProperties` means `true`, as in the standard. Closed Knotra control objects do
not change user schema rules. `default` inside DataSchema is an annotation, not value insertion.
Knotra always validates the model's final result itself, even if the provider API promises
structured output.

### Port variants

The common optional `description` field is a nonempty string.

| Location                                           | Additional fields                                                                                                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Pipeline.inputs`, `Graph.inputs` (`InputPort`)    | `required` defaults to `true`; optional `default: Json`, for JSON only                                                                                 |
| `Node.inputs` (`NodeInput`)                        | Required `bind: Binding`; `required` defaults to `true`; `mount: Path` is required for artifacts in agent/code and prohibited otherwise                |
| JSON output of llm/agent/code/human (`JsonOutput`) | Only `schema`/`schemaRef`; `required` defaults to `true`                                                                                               |
| File output of agent/code (`FileOutput`)           | Required `artifact` and `collect: {path: Path, mediaType: string}`. Single file only: `collection` is absent or `false`. The output is always required |
| `Pipeline.outputs`, `Graph.outputs` (`Export`)     | Required `bind`; `required` defaults to `true`                                                                                                         |
| `loop.state` (`LoopState`)                         | Required `initial: Binding`, `next: Binding`; no `required`, `default`, `mount`                                                                        |

`InputPort.default` is validated against its schema during preparation and inserted only when the
key is absent from input data. `required` is then checked. An explicit `null` is not replaced by the
default. Input and output port objects cannot contain unknown names. The DataSchema governs fields
inside user JSON.

`artifact.mediaTypes` is a nonempty unique list of exact MIME types without parameters or wildcards.
`collection: false` means a single file; `true` means an ordered file list that may be empty. All
collection members satisfy the specified types. `collect.mediaType` must appear in `mediaTypes`; a
file extension does not determine the type automatically.

An artifact exists only as an immutable engine-registered handle bound to bytes, size and SHA-256.
Run inputs receive it through engine upload/resolution; the exact network endpoint belongs to the
API. Between nodes it is passed through `from` or `coalesce` of such references. `expr`/`value`
computations, JSON Pointer and conversion from JSON to a handle are prohibited for artifact
bindings.

## 5. Binding and scopes

`Binding` is an object of exactly one of four kinds:

| Form                                    | Value                                                         |
| --------------------------------------- | ------------------------------------------------------------- |
| `{value: Json}`                         | JSON literal without interpolation                            |
| `{from: reference, path?: JSONPointer}` | Port value; an optional RFC 6901 Pointer selects part of JSON |
| `{expr: CEL string}`                    | Computation preserving the result's JSON type                 |
| `{coalesce: [Binding, Binding, ...]}`   | First present result in order; at least two alternatives      |

Allowed references are `inputs.<port>`, `nodes.<node>.outputs.<port>`, `args.<port>`,
`state.<name>`, `iteration.item`, `iteration.index`, `body.outputs.<port>`. Listing syntactic forms
does not mean all are available at every location.

| Evaluation location                               | Available context                                                                |
| ------------------------------------------------- | -------------------------------------------------------------------------------- |
| `Node.inputs.*.bind`                              | `inputs`, `nodes` of the current Graph                                           |
| `Node.when`                                       | `inputs`, `nodes`, already resolved `args` of the current node                   |
| `Graph.outputs.*.bind`, `Pipeline.outputs.*.bind` | `inputs`, `nodes` of the current Graph                                           |
| `tool.arguments`, `switch.cases[].when`           | Only `args`                                                                      |
| `foreach.with.*`                                  | `args`, `iteration.item`, `iteration.index`                                      |
| `loop.state.*.initial`                            | Only `args`                                                                      |
| `loop.with.*`                                     | `args`, current `state`, `iteration.index`                                       |
| `loop.until`, `loop.state.*.next`                 | `args`, current `state`, `iteration.index`, `body.outputs` of the completed body |

`inputs` are inputs of the current Graph, `args` are inputs of the current node, and `nodes` are its
neighbors. A foreach/loop body sees only its own inputs and nodes; outer values are passed through
`with`. Model history, neighboring files and secrets are unavailable in CEL. Iteration indexes start
at zero.

Node and port names in references must be statically known. CEL allows `nodes.review.outputs.score`;
computed access such as `nodes[args.node]` is prohibited. Access within user JSON values may be
dynamic. Dependencies are extracted from the parsed AST, including both branches of ternary
expressions and every coalesce alternative.

Absence differs from `null`: `coalesce` selects a present `null`. Every source must finish; a source
error is not a fallback alternative. A skipped output cannot be hidden through
`has(nodes.x.outputs.y)` or CEL short-circuiting. Use `coalesce` for alternative sources and
`required: false` for optional inputs. Full missing/skip/error rules are in
[execution](execution.md).

JSON Pointer: an empty string selects the whole value; `/a~1b` selects key `a/b`, `/a~0b` selects
`a~b`. An array index is `0` or a decimal number without leading zeros; `-` does not mean the
last/new element. An absent path yields missing; an invalid escape is a preparation error.

## 6. Common Node fields

Every node has a required `type` and fields for its type. Its name is the key in `nodes`.

| Field         | Rule                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `description` | Optional nonempty string                                                                            |
| `inputs`      | NodeInput map, default `{}`                                                                         |
| `needs`       | Unique neighboring node names, default `[]`; successful-completion dependency without data transfer |
| `when`        | CEL with a boolean result; absence means `true`; checked after input resolution                     |
| `execution`   | Optional `timeout`, `retry`, `onUnknownOutcome`                                                     |

`execution` merges with defaults field by field, including fields of `retry`; other language objects
do not automatically merge recursively. `retry.maxAttempts` is required inside an explicit `retry`:
1–100, including the first attempt. The default is one attempt; `backoff` defaults to `1s`, a
constant delay between permitted retries without exponential growth. `onUnknownOutcome` defaults to
`pause`; the alternative is `fail`.

Effective `retry.maxAttempts` must be 1 for switch/human/foreach/loop/pipeline. In particular, a
shared default with more attempts requires an override for these types. Retry does not authorize
repeating external effects: [execution](execution.md) determines whether each attempt is allowed.

When `execution.timeout` is not specified explicitly or through defaults: llm/agent/code/tool use
`30m`, human uses `24h`, switch uses `1m`, and foreach/loop/pipeline use the parent run's remaining
time. Local timeouts are bounded by ancestors' remaining time. They cover attempts and delays,
starting when the node becomes ready for execution.

## 7. Every node type

### llm

Required: `outputs: {port: JsonOutput, ...}` and `llm: {model, prompt}`. Optional:
`llm.instructions`. `model` is a local alias; `prompt` and `instructions` are TextSource. One
logical result generation, without tools or sandbox. Inputs are JSON only. The response is an object
keyed by output port names; arbitrary text instead of JSON is a result error.

A provider may make multiple transport attempts only under retry policy; every actual request
consumes budget. There is no separate unbounded JSON repair loop. Hidden transport retries within an
attempt are prohibited; a request failure ends the attempt.

### agent

Required: `sandbox`, nonempty `outputs`, `agent: {model, prompt, maxSteps}`. Optional:
`agent.instructions`, `env`, `tools`. `maxSteps` is the number of model calls in one agent attempt:
1–10000, including the first; repeated network requests are also bounded by the shared
`maxModelCalls`.

The agent receives only permitted MCP and built-in sandbox tools. `tools` has fields `inherit`
(default `true`), `mcp`, `sandbox`. With inherit=true, local grants are unioned with defaults.tools;
false starts with an empty set. The result is checked against the engine profile and ancestor
constraints; excess permissions are an error, not silently trimmed.

Completion uses the control tool `knotra.finish` with a JSON output object; the engine collects file
outputs. Control completion requires no user grant and does not count as an external tool call.
Final-step and finish-validation details are in [execution](execution.md). A new agent does not
inherit another node's conversation.

### code

Required: `sandbox`, nonempty `outputs`, `code: {command: Argv}`. Optional: `env`. The engine starts
one process with the specified argv in the sandbox. The first argument is resolved under OS/image
rules; a shell is used only when explicitly specified as the executable. Empty arguments after the
first are preserved. Success requires exit code 0 and validation of JSON/file outputs against the
[execution ABI](execution.md).

For code/agent, `env` maps variable names (`[A-Za-z_][A-Za-z0-9_]*`) to exactly `{value: string}` or
`{secret: local_alias}`. There is no `${ENV}`, implicit `.env` reading or copying of the CLI
environment. `KNOTRA_*` names are reserved by the engine.

### tool

Required: `tool: {server, name, arguments}` and `outputs: {result: JsonOutput}`. Other output names
are prohibited. `server` is a local MCP alias, `name` is the exact tool name, and `arguments` is a
Binding evaluated in args and returning a JSON object.

`tool.response` defaults to `structured`: result is the successful MCP response's
`structuredContent`; absence is an error, without automatic text parsing. In `content` mode, result
is an array of MCP content blocks as JSON. Successful JSON is validated against the declared result
schema; `isError: true` means failure regardless of content. No separate sandbox is created for this
node; a stdio server uses its environment from EngineProfile. MCP resources/prompts and sampling are
not standalone v1 language operations.

### switch

Required: `switch: {cases, default}`. `cases` is a nonempty ordered list of
`{name: Identifier, when: CEL}`. Conditions see args and return boolean. Every case name and the
default name are distinct. The first true condition wins; otherwise default is selected.

The node has one derived output `route`: a string from the set of case and default names. An
`outputs` field is prohibited. Branch names do not automatically start nodes with matching names:
downstream nodes read route and use `when`.

### human

Required: `human: {prompt: TextSource}` and nonempty JSON `outputs`. The engine saves the request,
text, input context and response schema, then waits for a response addressed by request ID. The
response is an object keyed by output names. Invalid responses are rejected; the request remains
open until timeout/cancellation. The first valid response applies once. Response UI and responder
authentication are described in the [API](../api/desktop-v1.md); responses are available through CLI
and desktop. A prompt does not automatically authorize an action.

### foreach

Required: `foreach: {over, concurrency, with, body}`. `over` names a declared input of the node
itself, containing a JSON array or artifact collection. `concurrency` is the positive maximum number
of concurrent iterations, in addition to the global limit.

`with` maps bindings to body inputs; it may be `{}`. `body` is a Graph. Each iteration receives its
own Graph and is numbered in the original array order. Body outputs must be required. Each JSON
output becomes an array of those values; a single file output becomes a collection. Exporting an
artifact collection from a foreach body is prohibited: no implicit flattening. Derived outputs use
body export names; foreach has no `outputs` field. Empty input produces empty arrays/collections for
every result. Failure of any iteration fails foreach.

### loop

Required: `loop: {maxIterations, with, body, until}`. Optional: `state` and
`onLimit: fail | return_last` (default fail). `maxIterations` is 1–100000 body executions. `state`
is a LoopState map; every value is initialized from args and validated against its own contract.

The loop executes its body at least once. `with` passes args/state/index to body inputs. After a
successful body, boolean `until` is evaluated; true ends the loop. If false on the last allowed
iteration, fail produces `ITERATION_LIMIT`, while return_last publishes the last body with
`termination: limit`. Otherwise all `next` values are evaluated simultaneously using the old state
and body results, validated, and replace the state for the next iteration. On termination, next is
not evaluated.

Derived outputs are the last body's exports and required `iterations` (integer count of body
executions) and `termination` (`condition` or `limit`). Therefore the body cannot export
`iterations`/`termination`. Final state is not published by itself: the body exports any needed
value. A loop has no `outputs` field.

### pipeline

Required: `pipeline: {file: Path, permissions}`. The file is a standalone Pipeline from the same
frozen package. Node inputs become called Pipeline inputs; its input defaults apply normally.
Outputs are derived from the called Pipeline's exports; an additional outputs field is prohibited.

`permissions` contains all four required fields: `models: [profile_model_id]`,
`mcp: {profile_server_id: [ToolName]}`, `sandboxes: [profile_sandbox_id]`,
`secrets: [profile_secret_id]`. An empty list/object explicitly permits nothing. Call permissions
are intersected with every ancestor's permissions and cannot expand them. Permission for a
model/server includes use of its credentials inside the trusted connection; `secrets` permits
separately giving a raw secret to a process. Full rules are in the
[engine profile](engine-profile.md).

Recursive imports are prohibited, including cycles through conditional branches. Child runs share
global budgets; calling a subpipeline does not reset limits.

## 8. Nested Graph

A Graph contains only `inputs` (optional), `nodes` and `outputs` (required nonempty maps). It
declares no models, permissions or defaults of its own and uses resources from the nearest Pipeline.
The dependency graph in every scope is acyclic; loop is a separate bounded construct, not permission
for backward edges.

`with` keys must exist in body.inputs. Every required input must have a binding or default. For a
particular iteration, missing is handled like an absent Graph input. All iterations are isolated;
access to a neighboring iteration's result is possible only after foreach aggregation or through
explicitly carried loop.state.

## 9. Prompts and context

TextSource is literal text: `${...}`, `{{...}}` and similar sequences have no special meaning. For
dynamic text, the author explicitly computes a JSON input through CEL or code. The engine passes
instructions, prompt and a separate typed input context with port names; data does not become
instructions through hidden template concatenation.

The normative context has the form `{values: {JSON ports}, artifacts: {file ports}}`; the exact
descriptor and file ABI are defined in [execution](execution.md). The adapter must preserve
separation of system instructions, task and input data within API capabilities. An llm model
receives JSON only. Human receives data and accessible input artifact references. Agent receives its
own inputs and mounted file paths, available tools, its history and finish schema.

## 10. Versions and v1 boundaries

Any change to an existing construct's meaning after v1 approval requires a new format version.
Unknown versions are rejected. Migration creates a new description; the engine does not rewrite an
old package automatically. Changes are recorded in Git history and undergo joint review of contract,
compiler and runtime. Workflow changes account for already saved histories.

v1 has no arbitrary plugins inside YAML, remote imports, secrets in expressions, unbounded loops,
recursive subpipelines, implicit shared memory, wildcard permissions, automatic model fallback,
catch/compensation graphs or recovery from an arbitrary process instruction. By default, an error
stops the corresponding run. These boundaries do not prevent full descriptions using all nine
declared constructs.

Transport is described in the [API](../api/desktop-v1.md), commands in the
[CLI](../../internal/cli/README.md), and supported adapters in the
[adapter documentation](../../internal/adapters/README.md). These boundaries preserve notation
semantics; network endpoints and Temporal details are not added to user Pipeline documents.
