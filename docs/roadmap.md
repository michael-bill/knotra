# Этапы разработки

Статус: согласованный порядок развития от 29 сентября 2026 года. Это план без обещанных сроков; реализация ещё не начата.

## Этап 1. Контракты первой версии

До реализации интерпретатора необходимо подготовить несколько полных примеров пайплайнов и проверить, что нотация выражает их без неоднозначностей.

Примеры должны покрыть:

- Последовательную передачу структурированных данных.
- Агентный кубик с моделью, MCP и файловым окружением.
- Кодовый кубик и передачу созданного файла.
- Условную ветку и объединение параллельных результатов.
- Ожидание ответа человека.
- Ошибку инструмента, повтор и неопределённый исход внешнего действия.

Результат этапа:

- Точная схема первого формата YAML и правила CEL-выражений.
- Формат пакета и привязок файлов.
- Модель состояний и правила переходов.
- Границы гарантий восстановления.
- Контракт API, событий и команд CLI.
- Выбор первого предметного сценария и провайдеров моделей.

## Этап 2. Минимальный путь исполнения

Реализовать приём и проверку пакета, фиксацию версии, запуск workflow Temporal и исполнение короткой последовательности кубиков.

В состав входят API, CLI, PostgreSQL, хранилище артефактов, базовые события и Compose для разработки. Первый внешний вызов модели выполняется через адаптер; проверка логики не должна требовать платных запросов в каждом тесте.

Критерий завершения: через CLI можно отправить процесс, увидеть состояния и получить проверенный структурированный результат; перезапуск компонентов сохраняет историю и корректно учитывает завершённые операции.

## Этап 3. Первая полезная версия

Добавить:

- Вызовы моделей и собственный агентный runtime.
- Кодовые кубики в Docker-окружениях.
- MCP через stdio и Streamable HTTP, прямой вызов инструмента.
- Передачу структурированных данных и файлов между кубиками.
- Условия, параллельное исполнение и ограниченный набор правил объединения.
- Сохранённые запросы к человеку и продолжение после ответа.
- Лимиты, отмену и документированную политику повторов.
- Историю действий, просмотр событий и получение артефактов через CLI.
- Несколько адаптеров моделей, выбранных по первым сценариям.

Критерий завершения: реальный процесс выполняется целиком, результат можно получить и проверить, ошибку можно локализовать, а поведение после сбоя соответствует опубликованным гарантиям.

## Проверки перед первой поставкой

| Сценарий | Ожидаемое свойство |
| --- | --- |
| Некорректный YAML или ссылка на отсутствующий кубик | Понятная ошибка до исполнения |
| Нет обязательного секрета или возможности модели | Ошибка подготовки запуска без начала зависимой работы |
| CLI отключён и подключён заново | Запуск продолжается, клиент восстанавливает события |
| Исполнитель остановлен после завершения кубика | Сохранённый результат учитывается при восстановлении |
| Внешний вызов выполнен, но подтверждение потеряно | Применяется политика идемпотентности или явно фиксируется неизвестный исход |
| Агент вернул неверную структуру результата | Кубик не объявляется успешным без проверки |
| Достигнут лимит шагов или времени | Работа останавливается по определённому правилу |
| Запрошен запрещённый инструмент | Вызов не выполняется независимо от текста промпта |
| Секрет подключения модели | Не наследуется автоматически sandbox и не включается в обычные логи |
| Артефакт передан другому кубику | Файл доступен по объявленной привязке без общей рабочей директории |
| Ожидание человека и перезапуск | Запрос сохраняется, ответ применяется к нужному запросу |
| Отмена во время исполнения | Новая работа не планируется; исход активных операций отражён корректно |
| Изменение исходного пакета после запуска | Выполняющийся процесс использует зафиксированную версию |

Восстановление состояния workflow и продолжение внутри файлового окружения проверяются отдельно. Первая поставка не должна обещать продолжение с произвольной инструкции программы или точное восстановление живого контейнера.

## Предполагаемые возможности CLI

Следующие команды показывают предполагаемый пользовательский интерфейс. Они ещё не реализованы; названия и параметры будут уточнены вместе с API.

| Команда | Назначение |
| --- | --- |
| `knotra validate pipeline.yaml` | Проверить пакет локально |
| `knotra run pipeline.yaml` | Отправить пакет на выполнение |
| `knotra runs list` | Получить список запусков |
| `knotra runs watch <id>` | Следить за событиями |
| `knotra runs cancel <id>` | Запросить отмену |
| `knotra runs respond <id>` | Ответить на сохранённый запрос к человеку |
| `knotra artifacts get <id>` | Получить результат |

Для команд чтения предусматривается машинный вывод. Поведение подключения, ожидания завершения, кодов выхода и повторной отправки команд определяется в спецификации CLI.

## Следующие расширения

- Обработка коллекций с ограниченной параллельностью.
- Явные циклы и переиспользуемые подпайплайны.
- Новый запуск с выбранного места и сравнение результатов.
- Более подробное восстановление агентного кубика с согласованным состоянием файлов.
- Набор примеров для оценки качества, времени и стоимости после изменения промптов или моделей.
- Объектное хранилище и исполнители на разных машинах.
- Дополнительные источники секретов и профили доступа.
- Усиленная изоляция для других моделей использования.
- Явная постоянная память между запусками.

Desktop-клиент остаётся отложенным направлением. Его разработка начинается после отдельного решения о возвращении к этому интерфейсу.

## Открытые решения

Архитектурный стек принят; следующие вопросы уточняют поведение первой версии:

1. Первый предметный сценарий и реальные критерии качества результата.
2. Поддерживаемые платформы и способ установки контейнерного окружения.
3. Точный формат YAML, выражений и файлового пакета.
4. Первый набор провайдеров моделей и MCP-возможностей.
5. Правила объединения веток, повтора и восстановления каждого типа операции.
6. Детализация workflow и Activities, контрольные точки и обновление исполнителей.
7. Политика сети, ресурсов, хранения файлов и освобождения sandbox при ожидании.
8. Аутентификация удалённого API и управление подключениями.
9. Сроки хранения событий, чувствительных данных и артефактов.

Выбор Temporal для первой версии уже сделан. Его замена или добавление отдельного локального исполнителя без инфраструктуры потребуют самостоятельного архитектурного решения.
