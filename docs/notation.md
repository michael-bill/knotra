# Нотация пайплайнов

Статус: согласованная модель нотации от 29 сентября 2026 года. Этот документ определяет содержание и принципы; точные имена полей и исполняемая JSON Schema ещё не утверждены.

## Формат

Главный документ пайплайна использует YAML 1.2. JSON Schema описывает его структуру и контракты входных и выходных данных. CEL используется для условий и ограниченных выражений над данными.

Нотация описывает сущности Knotra и не требует от пользователя знания Temporal. Она содержит версию формата, по которой движок определяет совместимость.

Пайплайн может состоять из одного YAML или пакета с соседними файлами: промптами, схемами, скриптами и другими объявленными материалами. Ссылки на такие материалы разрешаются относительно пакета. Произвольные файлы компьютера не включаются в пакет автоматически.

## Три вида конфигурации

| Вид | Примеры |
| --- | --- |
| Определение пайплайна | Кубики, связи, инструкции, контракты, логические подключения и требуемые возможности |
| Конфигурация размещения | Адреса сервисов, реальные подключения, источники секретов, ограничения движка |
| Параметры запуска | Пользовательские значения, входные файлы и разрешённые переопределения |

Пайплайн может закреплять конкретную модель или образ, когда это необходимо. Логические имена подключений позволяют использовать одно описание в разных окружениях.

Правила переопределения должны быть явными. Параметры запуска не могут произвольно расширять разрешения или обходить ограничения движка.

## Состав определения

| Раздел | Содержание |
| --- | --- |
| Метаданные | Идентификатор, название, описание, версия формата |
| Входы пайплайна | Типы, обязательность, допустимые значения и значения по умолчанию |
| Выходы пайплайна | Структурированные результаты и артефакты, доступные вызывающему |
| Подключения моделей | Логическое подключение, модель, параметры и необходимые возможности |
| Подключения MCP | Транспорт, ссылка на конфигурацию подключения, требуемые инструменты |
| Общие настройки | Значения по умолчанию и общие явно выданные возможности |
| Кубики | Идентификаторы, типы, входы, выходы и настройки исполнения |
| Зависимости | Привязки данных, порядок и условия запуска |
| Окружения | Образы, ресурсы, сеть, зависимости и размещение входных файлов |
| Политики | Лимиты, повторы, обработка ошибок и участие человека |
| Секреты | Требуемые логические ссылки без секретных значений |

Это смысловые разделы, а не окончательные названия ключей YAML.

## Типы кубиков

| Тип | Поведение | Этап |
| --- | --- | --- |
| Вызов модели | Один логический запрос с заданным контрактом результата | Первая полезная версия |
| Агент | Цикл модели и инструментов до завершения или лимита | Первая полезная версия |
| Код | Заранее написанная программа или команда в sandbox | Первая полезная версия |
| Инструмент | Прямой вызов объявленного инструмента без выбора действия моделью | Первая полезная версия |
| Условие | Выбор ветки по выражению над доступными данными | Первая полезная версия |
| Участие человека | Получение ответа, проверки или подтверждения | Первая полезная версия |
| Обработка коллекции | Выполнение вложенной операции для элементов с ограниченной параллельностью | Расширение |
| Цикл | Повторение вложенного процесса с условием завершения и лимитом | Расширение |
| Подпайплайн | Вызов зафиксированной версии другого пайплайна | Расширение |

Один логический вызов модели может иметь сетевые повторные попытки по политике исполнения. Это не превращает его в автономный агентный цикл.

## Контракт кубика

Каждый кубик определяет:

- Стабильный идентификатор и тип.
- Назначение и необязательное человекочитаемое описание.
- Источники входов и схему принимаемых данных.
- Структуру выходов и объявленные артефакты.
- Зависимости и условия запуска.
- Ограничения времени и ресурсов.
- Политику ошибок и повторных попыток.

Для агента дополнительно задаются модель, инструкции, доступные инструменты, правила контекста, окружение, предел числа действий и условия завершения.

Общие настройки уменьшают повторение, но итоговая разрешённая конфигурация каждого кубика должна быть однозначно вычислима и доступна для просмотра.

## Связи и выражения

Привязка входа указывает конкретный источник: параметр запуска, результат предыдущего кубика, значение выражения или артефакт.

Зависимость передачи данных и зависимость порядка имеют различимый смысл. Их точное представление в YAML будет определено так, чтобы избежать противоречивых дублирующих объявлений.

CEL применяется к ограниченному набору данных, доступных текущему кубику. Выражение не получает произвольного доступа к сети, файлам или секретам. Набор функций и вычислительные ограничения определяются движком.

Полноценный код выполняется в кодовом кубике. Разбор YAML и вычисление выражений не запускают произвольные программы на хосте.

Синтаксис вставок в промпты, привязок данных и CEL-выражений ещё предстоит определить. При этом привязка объекта или числа должна сохранять тип, а преобразование в строку должно быть явным и предсказуемым.

## Контракты данных

Входы и выходы описываются JSON Schema. Проверка выполняется перед передачей данных в кубик и перед публикацией его результата.

Отсутствующее значение, явный `null`, пропущенная ветка и ошибка источника должны различаться. Правила для этих случаев фиксируются в спецификации до реализации ветвления.

Артефакт передаётся по идентификатору, а размещение файла внутри sandbox задаётся отдельно. Объявление выходного файла включает его назначение и правила публикации; простого упоминания пути в ответе модели недостаточно для подтверждения результата.

Поддерживаемый профиль JSON Schema и ограничения конкретного API модели проверяются отдельно. Неподдерживаемые моделью ограничения нельзя молча считать выполненными; финальная проверка результата остаётся в Knotra.

## Модели, инструменты и контекст

Конфигурация модели включает логическое подключение или закреплённый провайдер, идентификатор модели и необходимые возможности. Специфические параметры провайдера должны иметь явно выделенную область.

Автоматическая замена модели допустима только по заданной политике и отражается в истории.

MCP-подключение и разрешение на его инструмент — отдельные сущности. Общие инструменты пайплайна и дополнительные инструменты кубика объединяются только в пределах разрешений движка.

Контекст агента включает инструкции, выбранные входы, объявленные материалы и историю его собственных действий. История соседнего кубика и память прошлых запусков передаются только явно. Постоянная память между запусками является последующим расширением.

## Секреты

В пакете хранятся ссылки на секреты. Значения разрешаются на стороне движка и передаются конкретным подключениям или разрешённым процессам.

Нотация различает секрет подключения модели, секрет MCP-сервера и секрет, явно доступный программе внутри sandbox. Выдача одного вида доступа не означает выдачу остальных.

Содержимое окружения пользователя не становится параметрами запуска автоматически. Экспорт пакета не должен включать секретные значения.

## Проверки

Проверки выполняются слоями:

1. Синтаксис YAML и допустимые типы значений.
2. Соответствие схеме формата.
3. Уникальность идентификаторов и корректность ссылок.
4. Корректность зависимостей и разрешённых конструкций графа.
5. Проверяемая совместимость контрактов данных и выражений.
6. Наличие материалов пакета и допустимость ссылок на них.
7. Наличие подключений, необходимых возможностей и прав на движке.
8. Проверка конкретных входных данных запуска.

Полная совместимость произвольных JSON Schema не обещается как статически разрешимая задача. Статические проверки выявляют известные противоречия, а реальные значения проверяются при исполнении.

Неизвестные поля и неоднозначные конструкции должны давать диагностируемую ошибку. Политика дублирующихся ключей, YAML aliases и внешних ссылок в схемах определяется в спецификации парсера с ограничениями размера и сложности.

Ошибка должна указывать файл, положение в документе и понятную причину, когда такая информация доступна.

## Версионирование

Версия формата отделена от версии конкретного пайплайна. Движок принимает только поддерживаемые версии формата и не изменяет смысл старого описания неявно.

Запуск фиксирует содержимое пакета, разрешённые настройки, идентификаторы моделей, сведения об образах и обнаруженных инструментах. Значения секретов в этот снимок не входят.

Изменение файла, промпта или привязки создаёт новое описание для следующих запусков. Продолжающийся запуск использует прежний зафиксированный план.

## Что предстоит специфицировать

- Точные поля, синтаксис привязок и шаблонов промптов.
- Правила значений по умолчанию и переопределений.
- Поддерживаемый профиль JSON Schema и CEL.
- Правила объединения веток, пропуска, ошибок и отмены.
- Формат ссылок на артефакты и пакетирование файлов.
- Ограничения парсера, разрешения ссылок и размер пакета.
- Формат версий и политика миграции.

Эти решения принимаются на нескольких полноценных примерах пайплайнов до реализации интерпретатора.
