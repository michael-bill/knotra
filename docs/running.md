# Запуск движка и CLI

Движок запускается нативным Go-бинарником и соединяется с PostgreSQL, Temporal, Ollama и Docker.
Compose ниже поднимает отдельную инфраструктуру для разработки; сам движок остаётся на хосте, чтобы
использовать локальные Ollama и Docker/Colima.

## Подготовка

Нужны Go версии из `go.mod`, Docker Engine и Make. На macOS Docker может работать через Colima. Для
примеров нужна установленная в Ollama модель `qwen3.5:9b`.

```sh
go version
docker info
ollama list
make build helper firewall
docker pull python:3.13-alpine
docker pull node:22-alpine
```

`make helper` определяет архитектуру Docker daemon. Если она недоступна при сборке, задайте
`HELPER_ARCH=arm64` или `HELPER_ARCH=amd64` явно. Бинарник CLI появится в `bin/knotra`, Linux-helper
— в `.knotra/bin/sandbox-helper`. Профиль sandbox может выбирать другой образ: helper не требует
Python или shell, но программа самого пайплайна должна присутствовать в выбранном образе.

## Вариант A: существующие PostgreSQL и Temporal

Используйте отдельную базу Knotra, не чужую базу приложения. Таблицы создаются движком при старте.
Temporal namespace должен уже существовать.

```sh
export KNOTRA_DATABASE_URL='postgres://127.0.0.1:5432/knotra?sslmode=disable'
bin/knotra serve \
  --profile examples/local/profile.yaml \
  --temporal-address 127.0.0.1:7233
```

Пользователь и пароль PostgreSQL определяются вашей установкой. Токены моделей и MCP задаются через
переменные окружения процесса движка, на которые ссылается `EngineProfile`; клиент их не получает.
Пример локального профиля не требует токена для Ollama. Выбранный Docker context используется
автоматически, либо можно задать `DOCKER_HOST` / `--docker-host` с URL локального Unix-сокета.

## Вариант B: инфраструктура в Compose

```sh
docker compose up -d --wait
export KNOTRA_DATABASE_URL='postgres://knotra:knotra-development@127.0.0.1:25432/knotra?sslmode=disable'
bin/knotra serve \
  --profile examples/local/profile.yaml \
  --temporal-address 127.0.0.1:27233
```

Если Homebrew установил отдельный `docker-compose`, используйте это имя вместо `docker compose`;
формат файла одинаков. Compose публикует порты только на loopback: PostgreSQL — `25432`, Temporal
gRPC — `27233`, Temporal UI — `28233`. Переменные `KNOTRA_PG_PORT`, `KNOTRA_TEMPORAL_PORT`,
`KNOTRA_TEMPORAL_UI_PORT` переопределяют их. `KNOTRA_DEV_DB_PASSWORD` меняет пароль при первом
создании базы; обновите строку подключения соответственно.

Compose использует закреплённые digest официальных PostgreSQL 18.6 и Temporal CLI 1.9.1. Том
PostgreSQL смонтирован в `/var/lib/postgresql`, как требует официальный образ PostgreSQL 18.
[Документация образа](https://hub.docker.com/_/postgres)

Temporal здесь — **development server с сохранением SQLite в named volume**. Он сохраняет историю
между рестартами контейнера, но не предназначен для production. Свойства режима и `--db-filename`
описаны в [документации Temporal](https://docs.temporal.io/cli/command-reference/server).

```sh
docker compose stop
docker compose start
```

Остановка сохраняет данные. `docker compose down` удаляет контейнеры, сохраняя именованные тома.
`docker compose down --volumes` удаляет также историю и базу; эта команда нужна только для
намеренного сброса окружения разработки.

## Первый запуск

В другом терминале, из корня репозитория:

```sh
bin/knotra validate examples/starter/hello/pipeline.yaml
bin/knotra validate examples/starter/hello/pipeline.yaml --remote --profile local
bin/knotra run examples/starter/hello/pipeline.yaml --profile local --wait
bin/knotra runs list
```

Модель создаст приветствие для входа `name`, кодовый кубик запишет его в `greeting.txt`, движок
опубликует артефакт. Этот небольшой сценарий проверяет подключение и сохранение результата.
Используйте ID из результата:

```sh
bin/knotra runs get RUN_ID --json
bin/knotra artifacts download ARTIFACT_ID --output greeting.txt
```

CLI проверяет размер и SHA-256 до записи файла. `--force` разрешает заменить уже существующий файл.
`--json` предназначен для скриптов; справочник команд доступен через `bin/knotra --help` и в
[документации CLI](../internal/cli/README.md).

Другие [готовые сценарии](../examples/starter/README.md) показывают исследование трёх вариантов
независимыми агентами с расчётом оценок и выбором подходящего варианта кодом, создание игры с
управляемым движком циклом генерации и фиксированных тестов, а также редакторский процесс с
согласованием человеком. Все четыре используют профиль `local` и `model_main`; Python-шагам нужен
`python_box`, игре — `node_box` с образом `node:22-alpine`. MCP-серверы и секреты не нужны.

Для `human`-кубиков:

```sh
bin/knotra requests list --run RUN_ID --all --json
bin/knotra requests respond REQUEST_ID --outputs response.json
bin/knotra runs watch RUN_ID
```

Ответ адресуется конкретному request ID. Если соединение потерялось после отправки команды,
`operations list` покажет её сохранённый ID, а `operations retry ID` повторно сверит исходную
команду с прежним ключом идемпотентности.

## Подключение desktop и browser preview

Движок по умолчанию слушает `http://127.0.0.1:8787`. Запустите приложение по
[desktop README](../app/README.md), укажите этот адрес в Settings и подключитесь. На странице
**Пайплайны** выберите **Привет, модель**, **Исследование по исходным материалам**, **Создать игру в
крестики-нолики** или **От брифа к согласованной публикации**. Новую копию можно создать через
**Новый пайплайн → Готовые сценарии**; при запуске выберите профиль `local`. Технические примеры и
прежнее приветствие доступны в категории **Примеры блоков**, отдельная категория **Демонстрация**
работает с готовыми результатами. При запуске движок проверяет admission и фиксирует текущий пакет;
редактирование черновика не меняет уже принятый запуск.

Для browser preview добавьте при старте движка:

```sh
bin/knotra serve \
  --profile examples/local/profile.yaml \
  --temporal-address 127.0.0.1:27233 \
  --cors-origin http://127.0.0.1:1420
```

Этот адрес должен точно совпадать с origin браузера. Native desktop использует Rust HTTP-клиент и не
требует CORS. Оба клиента читают тот же API и SSE; запросы человека доступны в Inbox, проверенные
файлы — в Artifacts. Закрытие приложения не отменяет запуск. Встроенный guided demo использует
локальные образцы данных.

## Данные, восстановление и границы развёртывания

PostgreSQL хранит определения, принятые запуски, проекции, запросы к человеку, outbox и журналы
внешних операций. Temporal хранит историю исполнения. Каталог `--data-dir` хранит файлы артефактов и
вынесенные payload-данные Temporal, а также временные материалы sandbox. Для восстановления нужны
**все три хранилища**. Одной копии PostgreSQL недостаточно. Не удаляйте `.knotra`, пока нужна
история.

Текущая поставка — один процесс API/worker на одном хосте. Если worker перемещается, ему нужны те же
сохранённые данные, profile references и совместимые helper/образы. Несколько хостов с независимыми
локальными `data-dir` не образуют корректный общий движок. Общий PostgreSQL сам по себе эту проблему
не решает. Для production нужны отдельно подготовленные Temporal, PostgreSQL, резервное копирование
файлов и выбранная модель совместного хранения; Compose не является production-рецептом.

После перезапуска движка завершённые внешние ответы читаются из журнала. Если исход записи
неизвестен или потеряна рабочая среда незавершённого агента, движок требует явного разрешения
состояния вместо повторного исполнения команды. `runs resolve` принимает доказанный исход и
проверенные выходы; `resume` не обходит эту проверку. Отмена не откатывает изменения во внешних
системах.

Контейнеры имеют собственный watchdog: после аварийного завершения процесса движка прекращение
heartbeat останавливает их примерно через 45 секунд. Agent/code дополнительно ограничены дедлайном
попытки. При следующем старте движок очищает оставшиеся контейнеры и временные каталоги только
своего engine ID. Рабочая среда незавершённой попытки при этом не восстанавливается из временных
файлов.

На текущем этапе реализован модельный адаптер **Ollama**. Наличие произвольного строкового
`provider` в контракте не означает готовность адаптеров всех поставщиков: неизвестный адаптер
отклоняется при admission. MCP поддерживает Streamable HTTP и stdio внутри изолированного
контейнера. Детали и пределы Docker backend, включая фильтрацию сети по зафиксированным IP, описаны
в [документации адаптеров](../internal/adapters/README.md).

Для прослушивания внешнего интерфейса движку требуются `KNOTRA_TOKEN`, `--tls-cert` и `--tls-key`.
Удалённый CLI требует HTTPS и тот же токен. `--cors-origin` разрешает ровно один browser origin.
Текущий bearer token задаёт один доверенный principal; это не многопользовательская RBAC-система.

## Наблюдаемость и эксплуатационные ограничения

Логи сервера — JSON в stderr. `--debug` включает дополнительные сообщения. Трассы HTTP-запросов и
попыток кубиков, счётчик HTTP-запросов и их длительность можно отправлять по OTLP/HTTP, задав
`OTEL_EXPORTER_OTLP_ENDPOINT` либо отдельные `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` /
`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`. Без явного endpoint экспорт выключен.
`OTEL_SDK_DISABLED=true` отключает его. В атрибуты не включаются промпты, тела запросов, входные
значения и credentials.

Один engine ID обслуживается одним процессом: владение закрепляется отдельным соединением
PostgreSQL. Это ограничение развёртывания, а не параллельности запусков. Движок одновременно
исполняет несколько пайплайнов и несколько экземпляров одного YAML с независимыми лимитами и
sandbox. Имя Temporal task queue автоматически дополняется engine ID, чтобы разные базы движков не
забирали чужие задачи.

Списки имеют курсор и ограничиваются числом записей и объёмом. CLI-флаг `--all` обходит все
страницы. Артефакты входа видимы после загрузки; созданные кубиком — после проверки и публикации его
выходов. Для разрешения неизвестного исхода artifact-выход задаётся зарегистрированным ID (или
массивом ID для коллекции).

Файлы хранилища и история сейчас сохраняются без автоматической очистки. Оператор обеспечивает
свободное место и резервные копии; удалять файлы вручную при сохранённых запусках нельзя.
Максимальный размер отдельного артефакта — 64 MiB. Сетевой `allowlist` Docker фильтрует закреплённые
адреса, а не HTTP Host/SNI: доступ к разрешённому внешнему прокси означает доступ к его прикладным
функциям.

`resources` показывает доступные по установленным профилям ресурсы и выданные инструменты;
отсутствие обязательного секрета отмечается как `unavailable`. Это каталог конфигурации. Текущая
связь с сервисом, возможности конкретной модели, схемы MCP и доступность образов проверяются
командой `validate --remote` и при принятии каждого запуска.
