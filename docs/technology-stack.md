# Технологический стек

Статус: стек согласован 29 сентября 2026 года. Конкретные совместимые версии зависимостей будут закреплены при начале реализации.

## Выбранные технологии

| Область | Технология | Назначение |
| --- | --- | --- |
| Движок, API и исполнители | Go | Сетевая работа, управление параллельными операциями и окружениями |
| CLI | Go + Cobra | Команды, флаги, справка и автодополнение |
| Описание пайплайна | YAML 1.2 | Читаемое и версионируемое определение |
| Парсер YAML | goccy/go-yaml | Разбор документа и диагностика |
| Контракты | JSON Schema | Формат нотации, входов и выходов |
| Проверка JSON Schema | santhosh-tekuri/jsonschema | Проверка схем и значений в Go |
| Выражения | CEL, реализация cel-go | Условия и вычисления над объявленными данными |
| Надёжное исполнение | Temporal + Go SDK | Workflow, Activities, ожидания, история и восстановление |
| API | HTTP/JSON + OpenAPI | Контракт между клиентами и движком |

| Модели | Собственные адаптеры поверх SDK или API провайдеров | Подключение моделей с учётом их возможностей |

## Go

Движок управляет внешними API, долгоживущими операциями, процессами и контейнерами. Go подходит для такого сервиса и позволяет использовать один язык для API, исполнителей и CLI.

CLI поставляется готовым исполняемым файлом для поддерживаемой платформы. Это не означает, что вся система работает без отдельных сервисов.

Язык ядра не ограничивает программы кубиков. Python и другие необходимые инструменты устанавливаются в образы sandbox. Пользовательские библиотеки для обработки данных не загружаются в процесс оркестратора.

## Нотация

[goccy/go-yaml](https://github.com/goccy/go-yaml) выбран для работы с YAML. [santhosh-tekuri/jsonschema](https://github.com/santhosh-tekuri/jsonschema) поддерживает проверку JSON Schema, включая Draft 2020-12. Конкретный профиль нотации определим отдельно.

[CEL](https://cel.dev/) и [cel-go](https://github.com/google/cel-go) используются для ограниченных выражений. Доступные функции и значения задаются Knotra. Это позволяет держать условия частью декларативного описания.

Схема формата должна иметь единый источник истины и проверяться на согласованность с типами движка. Выбор между генерацией схемы и генерацией типов остаётся деталью реализации.

## Temporal

[Temporal Go SDK](https://docs.temporal.io/develop/go) используется с начала реализации исполнения. Это позволяет проектировать ожидания, перезапуски и повторные попытки на общей основе.

Temporal предоставляет историю и восстановление workflow; правила кубиков, разрешений и результатов задаёт Knotra. См. [модель Workflow Execution](https://docs.temporal.io/workflow-execution).

Компромиссы:

- Требуется отдельный сервис и постоянное хранилище Temporal.
- Логика workflow должна быть детерминированной.
- Обновления исполнителей должны учитывать старые запуски.
- Внешние операции могут требовать повторного исполнения и защиты от дубликатов.
- Файлы sandbox и внешнее состояние не восстанавливаются автоматически вместе с workflow.

Особенности повторного исполнения и идемпотентности описаны в [документации Activities](https://docs.temporal.io/activity-definition).

Выбор Temporal означает, что первая поставка ориентирована на полноценный движок с инфраструктурой. Режим исполнения без Temporal не входит в согласованный первый этап.

## PostgreSQL и артефакты

Для базы Knotra используется PostgreSQL с драйвером [pgx](https://github.com/jackc/pgx). Схема базы управляется версионируемыми миграциями.

Данные приложения и внутренние данные Temporal разделяются. Для первого развёртывания допустим один сервер PostgreSQL с отдельными базами.

Файлы хранятся отдельно от таблиц метаданных. Первый backend использует файловое хранилище на одной машине. Интерфейс хранения предусматривает последующий адаптер S3; конкретный поставщик объектного хранилища не выбран.

## Модели и агентный runtime

Knotra реализует собственный агентный runtime с контролем инструментов, контекста, лимитов и результата. Адаптеры скрывают транспортные различия провайдеров и сохраняют сведения об их возможностях.

Первый набор провайдеров выбирается по реальным сценариям. Для каждого адаптера проверяются необходимые возможности и поведение при потоковой выдаче, ошибках и повторах. Общая совместимость API не означает одинаковое поведение всех моделей.

## MCP

Используется [официальный MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk). Поддерживаемая версия протокола и необходимые возможности фиксируются вместе с версией SDK.

Начальный охват включает клиентские подключения через stdio и Streamable HTTP. Авторизация и управление жизнью запускаемых серверов входят в интеграцию Knotra.

## Docker

Исполнители управляют окружениями через [Docker Engine API и Go SDK](https://docs.docker.com/reference/api/engine/sdk/). Доступ к этому API остаётся у доверенного компонента.

Docker подходит для первой версии под своим управлением при ограниченной конфигурации окружений. Его модель изоляции и зависимость от настроек описаны в [документации безопасности Docker](https://docs.docker.com/engine/security/).

На macOS Linux-контейнеры требуют соответствующего контейнерного окружения. Поддерживаемые операционные системы и способы его установки будут зафиксированы перед первой поставкой.

Для усиленной изоляции позднее рассматриваются [gVisor](https://gvisor.dev/docs/) и [Firecracker](https://firecracker-microvm.github.io/). Это отдельные варианты реализации sandbox с собственными требованиями и ограничениями совместимости.

## CLI, API и диагностика

[Cobra](https://github.com/spf13/cobra) используется для CLI. Вывод предназначен как для человека, так и для автоматизации через JSON и определённые коды завершения.

HTTP API описывается через OpenAPI. SSE передаёт события. Формат событий включает идентификаторы, позволяющие восстановить чтение и обработать повторную доставку.

Структурированные логи связываются с идентификаторами исполнения. [OpenTelemetry для Go](https://opentelemetry.io/docs/languages/go/) используется для технических трассировок и метрик. Конкретная система их сбора не обязательна для первого локального запуска.

## Поставка и проверки

Первое развёртывание использует [Docker Compose](https://docs.docker.com/compose/) и постоянные тома для необходимых данных. API и исполнители Knotra, Temporal и PostgreSQL запускаются на одной машине; sandbox создаются по мере исполнения.

Проверки реализации будут включать стандартные тесты Go, проверку гонок, проверки парсера на некорректных входах и интеграционные сценарии с инфраструктурой. Особое внимание уделяется восстановлению, идемпотентности и ограничениям доступа.

Команды установки, закреплённые версии и конфигурация Compose появятся вместе с работающей реализацией. Примерные команды CLI приведены в [этапах разработки](roadmap.md), а не как уже существующий интерфейс.
